# Claude Design 전달: 바자울 모바일 문서 상세

기준일: **2026-10-05 (한국시간)**. 운영 main `e346cb0`와 직원용 1.0.5의 최신 문서함 배포를 기준으로 한다. 기존 Claude Design 작업 **바자울 전자결재 앱 디자인**의 새 페이지 **문서 상세 v1**을 만든다. 이미 완성·적용한 홈 v2와 문서함 v1을 보존하고 시각 체계를 이어간다.

이번 목적은 문서함/받은결재/홈에서 문서를 연 직원이 **누가 어떤 문서를 올렸는지, 현재 결재 상태와 본문·첨부의 근거, 본인이 할 수 있는 다음 행동**을 빠르고 정확하게 확인하게 하는 것이다. 네이티브 모바일 상세 화면이며 랜딩 페이지가 아니다. 운영 앱 코드 수정이나 배포는 이번 Claude 요청 범위가 아니다.

## 전달 자료와 우선순위

1. 이 브리프: 범위, 정보 순서, 업무 규칙, 모의 데이터, 검수.
2. UI/UX 가이드: 밀도·읽기·접근성·오류 예방의 필수 기준.
3. 현재 문서 상세 계약: 실제 응답 필드·권한·확인과 처리 흐름·공유 토큰.
4. 실제 적용 홈 v2 이미지: 브랜드·색·타이포·간격·아이콘 기준.
5. 실제 적용 문서함 v1 이미지 및 기존 캔버스: 상세로 이어지는 시각·탐색 기준.
6. 현재 상세 기능 참고 이미지: 모의 직원 문서로 실제 앱 코드를 렌더한 것. 이전 카드·큰 여백·색·아이콘을 그대로 복제할 기준이 아니다.

## 화면 범위와 탐색

- 상세는 탭 위에 열리는 **Stack 화면**이다. 상단에 뒤로·짧은 화면 이름을 두고, 문서 제목은 본문 상단에 명확히 표시한다. 상세 안에 탭바나 새 기안 버튼을 추가하지 않는다.
- 문서함에서 돌아오면 기존 분류·검색 조건·정렬·페이지를 유지하며 목록을 다시 조회한다. 받은결재나 홈 진입은 각 출발 화면으로 돌아간다. ‘문서함으로’로 모든 복귀를 고정하지 않는다.
- 같은 화면의 본문, 첨부 목록, 결재 진행, 처리 이력, 권한별 결재/회수/편집과 확인·오류 상태까지 설계한다.
- 첨부 미리보기/저장/공유, 기안 편집·재상신은 **기존 별도 화면으로의 모의 목적 안내**까지만 한다. 이들 후속 화면을 새로 디자인하지 않는다.
- 검토용 역할·문서 상태·테마·크기·글자·키보드·네트워크 컨트롤은 앱 화면 밖에 둔다.

## 정보와 읽기 우선순위

상단에서 제목·상태·문서번호, 기안자, 상신 시각, 본인에게 가능한 행동을 파악하게 한다. 반려 상태면 **현재 반려 사유·실제 처리자·시간**을 본문보다 먼저 확인하게 한다. 그 다음 본문과 첨부를 읽고 결재 진행과 처리 이력을 확인한다. 기안 정보의 작성일·완료일·문서 양식은 읽기 흐름을 밀지 않게 정리하되 없애지 않는다. 처리 이력은 본문·첨부 뒤의 참고 정보다.

대시보드·목록의 ‘첫 행 40%’ 목표를 이 상세 화면에 기계적으로 적용하지 않는다. 대신 첫 뷰포트에 제목·상태·기안자·상신 시각·본문 시작 또는 반려 이유와 필요한 주 행동이 보이게 한다. 임의의 KPI, 결재 소요 시간, 마감/긴급, 금액 요약, 새 섹션 메뉴로 첫 화면을 채우지 않는다.

본문은 **문자열**이다. 줄바꿈과 긴 내용 전체를 읽을 수 있게 한다. 전용 금액/품목/표/원문 PDF 필드가 없는 문서에 그런 구조를 실제 데이터처럼 만들지 않는다. 본문에서 텍스트 금액을 표현하는 것과 API의 별도 요약 금액을 발명하는 것은 다르다. 본문·처리 의견을 좁은 중첩 스크롤 상자에 가두거나 두 줄로 잘라 숨기지 않는다. 긴 제목도 상세에서는 전문을 읽을 수 있게 한다.

메타와 이력의 날짜는 한국 시간으로 연도·월·일·시·분을 표시한다. 값이 없으면 기록 없음이나 아직 상신하지 않음으로 사실대로 표현하고 추정하지 않는다.

## 권한과 행동

| 사용자·상태 | 허용 행동 |
| --- | --- |
| 일반 직원, 자신의 상신/결재 중 문서, `canRecall=true` | 열람 + **회수하고 수정** |
| 작성자, 본인의 임시저장/회수, `canEdit=true` | **기안 수정** 또는 **수정·재상신**, 기존 편집 화면으로 연결 |
| 시설장, 본인 결재 차례, `canDecide=true` | 첨부·본문 확인 후 **승인 / 반려** |
| 시설장이지만 본인 차례가 아님 | 열람만. 결재 버튼을 생성하지 않음 |
| 승인·반려 완료 문서 | 열람. 완료 문서 직접 수정·회수·승인 취소 없음 |
| 현재 결재자 + 미리보기 미지원 첨부가 있음 | 첨부 저장·공유 진입은 가능하나 앱 결재 불가. 서버의 `decisionBlockedReason`을 표시하고 웹에서 확인 후 결재하도록 안내 |
| 관리자 | 관리자라는 이유만으로 결재/다른 직원 기안 편집/회수 권한을 만들지 않음. 서버가 허용한 문서만 열람 |

클라이언트는 `canDecide`, `canRecall`, `canEdit`, 현재 사용자 `canApproveDocuments`를 사용한다. 이름이나 문서 상태만 보고 권한을 추정하지 않는다. 승인·반려는 시설장 직급 **AND** 본인 순서 **AND** 미리보기 제한 충족이다. `decisionBlockedReason`은 실제 응답이 있을 때만 보여준다.

반려 완료 문서에는 ‘수정·재상신’ 버튼을 새로 만들지 않는다. 현재 정책은 임시저장·회수 문서만 편집이다. 대리 승인·대리결재 반려 기록은 읽을 수 있지만 앱에 대리 처리 버튼은 없다. 폐기/복원/삭제/날인/서명본 생성/즐겨찾기/공유 링크/오프라인 저장 같은 동작을 추가하지 않는다.

## 승인·반려·회수의 안전한 모의 흐름

- 승인/반려 선택 → 의견 입력 → 확인 → 처리 중 → 성공하여 진입 화면 복귀. 단순 버튼 탭만으로 완료 처리하지 않는다.
- 승인 의견은 선택, 반려 사유는 공백 제거 후 **2~2000자**, 모든 의견은 **2000자 이하**다. 오류 후 입력을 보존하고 오류 칸/요약에 포커스. 장문의 사유와 키보드가 열렸을 때 확인·취소가 가려지지 않게 한다.
- 마지막 확인은 문서 제목, 승인/반려의 실제 결과와 취소를 명확히 표시한다. 취소·닫기·Escape·뒤로 후 실행한 요소로 포커스가 돌아가게 한다. 확인 취소로 입력을 지우지 않는다.
- 처리 중에는 확인뿐 아니라 충돌하는 승인/반려 전환·취소·회수·뒤로 등 중복 업무 실행을 막고 진행 상태를 읽을 수 있게 한다. 검수용 프로토타입에서 더블 탭도 한 번만 처리한다.
- 실패 시 ‘처리 완료’로 보이지 않게 하고 의견을 유지한 재시도/최신 상태 확인을 제공한다. 상태·권한이 바뀌면 현재 서버 상태로 다시 확인해야 하며 더 이상 허용되지 않는 행동을 숨기거나 명확히 막는다. 응답이 불명확한 경우 즉시 같은 업무가 성공했다고 추정하거나 자동 재실행하지 않는다.
- 회수는 ‘결재 진행을 중단하고 수정 화면으로 이동, 회수 기록 보존, 재상신 시 처음부터 결재’를 확인한 후 모의 진행한다. 버전 충돌/실패는 오류와 최신 상태 확인을 제공한다. 회수 성공 후 편집은 목적 안내로만 연결한다.
- 모의 프로토타입의 업무 변경은 가상 문서 상태에만 적용한다. 실제 API·로그인·푸시·파일 전송을 하지 않는다.

## 첨부와 결재 진행·이력

첨부는 이름, 원본/서명본, 파일 크기, 미리보기 가능 여부를 표시하는 compact 행이다. PDF·이미지에는 미리보기·저장·공유, 미지원 형식은 저장·공유 목적이 있음을 표현한다. 전체 파일명에 접근 가능하고 긴 파일명이 다른 정보를 덮지 않게 한다. 서명본은 원본과 구분하고 `signedAt`이 있을 때만 실제 시각을 쓸 수 있다. 서버 저장소 URL/키/토큰을 표시하거나 가짜 파일을 실제로 받게 하지 않는다.

결재 진행은 순서, 원 결재자 이름, 상태, 실제 처리자·시각, 기록된 의견을 확인한다. 상태는 결재 대기/차례 대기/승인/반려/대리 승인/대리결재 반려를 구분한다. 대리 처리자를 원 결재자로 잘못 표시하지 않는다. ‘승인 n/m’은 실제 단계에서 계산할 수 있으나 진행률 하나로 상태·순서·의견을 대체하지 않는다. 현재 상신 문서는 시설장 1명이 기본이나 과거 다단계 문서도 렌더할 수 있다.

현재 반려 이유는 현재 반려 상태의 최신 rejected 단계에서만 강조한다. 회수 후 재상신된 정상 문서에 이전 반려를 현재 경고로 띄우지 않는다. 현재 강조한 의견을 같은 화면의 단계 행에 중복 출력하지 않는다.

처리 이력은 최근순으로 **5건**부터, ‘더 보기’가 이전 **최대 10건**을 추가하고 접으면 최근 5건으로 돌아간다. 행에는 action/actorName/createdAt/description만 사용한다. 업무 기록 전문은 읽게 하고 내부 audit 메타·기기·IP·위치 값을 넣지 않는다. 빈 배열은 ‘아직 처리 이력 없음’, 서버가 histories를 주지 않는 경우는 업데이트 후 확인 필요로 구분한다.

## 대표 모의 데이터

모든 이름·문서·파일·시간·본문·의견은 가상 데이터다. 김예시(직원/기안자), 이예시(시설장/현재 결재자), 박예시(다른 시설장), 관리예시(관리자·결재 권한 없음)만 사용한다. 실제 직원·청소년·개인·운영 기록을 조회하지 않는다.

메인: **시설장 이예시 · 390×844 · 라이트 · 본인 순서 상신 문서**. 제목 ‘프로그램 운영비 지출결의’, EA-2026-0147, 지출결의서, 기안자 김예시. 작성 2026.10.5 09:00, 상신 09:12(KST), 결재자 이예시(1단계 pending). 본문은 공용 재료 사용 목적·운영 일정·첨부 계획서 참고를 여러 문단으로 작성한다. 첨부 ‘10월_운영계획서_모의.pdf’ 418KB와 ‘공용물품_참고사진_모의.png’ 183KB, 원본 2개. 실제 금액 요약 필드를 추가하지 않는다.

같은 문서의 기안자 열람에서는 canRecall=true, canDecide=false. 반려 변형은 ‘품목별 사용 목적과 운영 일정을 보완해 주세요.\n일정을 확인한 뒤 다시 제출해 주세요.’, 실제 처리자 이예시, 시각 10:00. 길이 변형은 긴 한글 제목·800자 이상 본문·여러 문단의 의견·긴 파일명·이력 18개. 과거 다단계는 김예시가 작성하고 이예시 approved, 박예시 pending, 세 번째 가상 시설장 이름은 임의 생성하지 말고 두 시설장으로 2단계를 구성한다. 대리결재 변형은 실제 처리자가 원 결재자와 구분되게 관리예시를 기록에만 사용한다.

## 시각과 산출물·검수

홈 v2·문서함 v1의 토큰, 4/8/12/16/24 간격, 얇은 경계, 절제된 파랑, 선형 아이콘을 이어간다. 기존 아이콘 라이브러리를 사용한다. 터치 영역 44×44 이상, 텍스트 4.5:1·컨트롤 경계와 상태 3:1을 확인한다. 처리 행동은 허용된 사용자에게만 의미 색상으로 보인다. 390×844와 360×800, Safe Area 가정 상단 47/24·하단34/16을 기록한다.

새 페이지 ‘문서 상세 v1’에 메인과 필요한 변형, 편집 가능한 소스·검토 프로토타입을 제공한다. 변형은 기능 경계마다 확인할 수 있으면 일부를 검토용 컨트롤로 묶어도 된다.

- 시설장 승인·반려 입력, 검증 오류/입력 보존, 마지막 확인 취소·포커스 복귀, 처리 중/중복 방지, 실패 후 재시도·최신 상태 확인, 성공 복귀.
- 기안자의 상신/회수 확인·실패, 임시저장/회수 편집 목적, 완료·반려 열람, 차례 아닌 시설장, 미지원 첨부 결재 차단.
- 반려 사유·대리 승인/대리결재 반려, 다단계·순서·의견, 이력 5→15→18 및 접기, 첨부 없음·본문 없음·이력 없음·미제공.
- 초기 로딩/오류/재시도, 권한 없음/없는 문서(내용 숨김), 기존 정보 갱신 실패(이전 상태 안내, 상태 변경 재확인).
- 360×800 긴 문서·파일명·의견, 라이트/다크, 200% 상당 큰 글자와 키보드 열린 의견·확인 버튼.

## 실제 앱 구현 후보 (2026-10-05)

Claude Design의 **문서 상세 v1**(26개 상태 시안과 검토용 프로토타입)을 받아 기존 Expo 앱에 구현했다. 원본은 [바자울 전자결재 앱 디자인](https://claude.ai/cowork/cse_019QmmgaB7zLPe4E3LvQLRnB?artifact=82497355-1c7d-45ce-933b-9e3b90d2ed7a)에 있고, 메인·권한·결재/회수 흐름·빈 상태·작은 화면·다크 시안을 기준으로 한다.

상단 Stack 헤더, 문서 정보, 본문·첨부, 현재 반려 사유, 결재 진행과 최근 5건/10건 추가 이력을 적용했다. 승인·반려는 의견 입력과 최종 확인을 거치며, 실패해도 입력을 보존하고 수동 최신 상태 확인 전에는 업무를 자동 재실행하지 않는다. 처리 직전에 최신 권한·상태·버전을 다시 조회하고 회수에는 `expectedUpdatedAt`을 전달한다. 권한이 없어지면 이전 문서와 열린 확인 창의 내용을 제거한다. 승인·회수 권한이 함께 있는 작성자의 회수 기능도 보존했다.

390×844·360×800, 라이트·다크, 긴 문서와 파일명, 전체 UI 200% 확대 및 키보드 점유 높이 모의 상태를 브라우저에서 확인했다. OS 기본 글꼴을 유지하며, 실제 iOS/Android 동적 글자 크기·키보드·스크린리더·파일 저장/공유는 실기기 후속 확인이다. QA 근거는 저장소 루트 `design-qa.md`와 `docs/design/mobile-document-detail-v1/`에 있다.

이 기록은 **구현 후보와 로컬 검수**다. 운영 main 병합과 직원용 EAS Update 배포는 아직 수행하지 않았다. 서버 계약·네이티브 구성·의존성을 바꾸지 않는다.
