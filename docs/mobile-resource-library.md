# 모바일 자료실과 웹 공유 정책

모바일 프로필의 자료실에서 법인·카페·바자울·교육 자료를 조회·검색하고 등록·수정·삭제한다.
교육은 공통·고등·중등으로 구분한다. 일반 목록은 3개, 교육 목록은 10개씩 페이지를 나눈다.
모든 ACTIVE 직원은 자료를 읽고 등록할 수 있으며, 수정·삭제는 작성자와 현재 ADMIN만 가능하다.
시설장이라는 이유로 다른 직원의 자료를 관리할 권한을 추가하지 않는다.

## 읽기와 변경

모바일 `/api/mobile/resources`는 기존 모바일 Bearer 세션을 사용한다. 서버는 매 요청마다
현재 계정 상태와 권한을 다시 확인한다. 목록·상세·편집 기준·열람자·첨부 조회 GET은 데이터를
변경하지 않는다. 실제 상세 진입의 열람 기록은 `/[id]/views` POST와 안정된 요청 키로 기록한다.
새로고침이나 응답 재시도로 같은 방문이 두 번 기록되지 않는다. 확인 직원 수와 개인 방문 횟수는
다른 값이며, 열람 기록은 자료 내용의 수정 기준을 바꾸지 않는다. 기존 웹 상세의 방문 집계는
웹 호환 래퍼에서 유지한다.

등록·수정·삭제 요청은 actor와 요청 키에 묶인 영수증을 하나의 DB 트랜잭션에서 남긴다.
수정·삭제에는 정확한 `updatedAt` 기준이 필요하다. 같은 요청 키의 다른 본문은 거절하며,
이미 처리된 같은 요청은 영수증을 먼저 확인한다. 삭제된 자료를 이전 등록 요청의 재시도로
다시 만들지 않는다. 원래 처리 시점과 현재 자료의 내용은 별도로 취급한다.

앱과 웹 폼은 중복 실행을 막고, 통신 결과가 불명확하면 원래 입력·첨부·요청 키를 유지한다.
재시도는 본인 영수증 조회부터 시작한다. 동시 수정은 사용자가 최신 기준을 명시적으로 선택한
뒤에만 새로운 요청으로 저장한다. 계정·권한 변경과 늦게 끝난 이전 계정의 비동기 응답은
기존 입력·파일과 새 세션에 섞이지 않도록 차단한다.

## 첨부

기존 관리자 첨부 정책의 확장자·개수·전체 용량 한도(최대 300MiB)를 공유한다.
새 첨부는 actor·자료 대상·용도에 묶인 업로드 영수증을 사용하며 전체 SHA256과 실제 서버에서
검증한 크기가 일치해야 자료에 소비된다. 원래 파일명·임의 저장소 키를 보내 기존 파일을
새 첨부로 연결하는 방법은 허용하지 않는다. 기존 자료의 첨부 조회는 유지한다.

Supabase의 임시 업로드 키와 최종 파일 키는 분리한다. 파일은 조각 단위로 해시·암호화·복호화하며
큰 파일 전체를 JS 버퍼 하나에 담지 않는다. 설치 앱은 BlobUtil 파일 스트림·Android 저장 선택·
iOS 공유와 기존 PDF 뷰어를 사용한다. 계정 변경 시 캐시와 임시 파일을 정리한다.
미리보기·다운로드는 현재 권한, 실제 파일 형식, 크기와 해시, 설정된 암호화 인증을 확인한다.

웹도 같은 업로드/변경 도메인을 사용한다. Supabase 직접 업로드가 가능한 경우 브라우저에서
파일을 나누어 해시하고 서버가 발급한 제한된 저장소 업로드 권한을 사용한다. 다른 저장소 또는
JavaScript가 없는 폼은 인증된 서버의 `File.stream()` 경로를 사용한다.

## 파일 정리와 배포

추가 마이그레이션은 `20261003120000_resource_mobile_receipts`이며 서버 전용 영수증·업로드·
방문 키·파일 정리 테이블 4개를 만든다. 기존 업무 행을 삭제하거나 수정하지 않는다.
4개 테이블에 RLS를 켜고 익명·클라이언트 Data API 정책은 만들지 않는다. 새 서버를 배포하기
전에 기존 배포 절차의 DB 대상·마이그레이션 이력을 확인하고 `npm run db:deploy`를 실행한다.
운영 DB에 `db:seed`, `migrate dev`, `db push`는 실행하지 않는다.

자료 저장·삭제가 완료되면 파일 정리 실패 때문에 업무 결과를 실패로 바꾸지 않는다.
남은 정리는 서버 큐에서 재시도하며 현재 참조·진행 중인 작업·유효한 업로드 권한을 보호한다.
쓰기가 끝났는지 확인할 수 없는 파일은 한 번의 부재 조회만으로 정리 완료라고 판단하지 않는다.
정리 중 영수증의 파일 이름·해시 등 일반 메타데이터는 즉시 지운다.

`vercel.json`은 `GET /api/internal/resource-maintenance`를 매일 18:00 UTC에 호출한다.
운영 호스트에 별도 무작위 `CRON_SECRET`(최소 16자)을 등록해야 인증된 예약 실행이 가능하다.
해당 값은 클라이언트나 저장소에 공개하지 않는다. 누락·잘못된 인증 요청은 DB/저장소를 열기
전에 거절한다. 이 경로는 ACTIVE 계정이 사라진 뒤의 만료 업로드도 제한된 작업량으로 정리한다.
예약 실행의 실제 설정과 완료 여부는 운영 배포 확인에 포함한다.
