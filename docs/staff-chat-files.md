# 직원 채팅 파일 전송

직원 1:1 채팅에서 메시지에 파일 한 개를 첨부할 수 있다. 수신자가 처음 다운로드하면
파일 원본을 저장소에서 삭제하고 대화에는 파일명·크기와 삭제 상태를 남긴다.
파일 바이트를 DB에 넣지 않고 기존 첨부파일 저장소를 사용한다.

## 삭제 시점

수신자 브라우저가 파일 전체를 받아 다운로드를 시작한 뒤 서버에 완료를 알리는 시점에
삭제한다. 채팅창 열기, 메시지 읽음 처리, 발신자의 다운로드는 삭제를 일으키지 않는다.
다운로드 중 네트워크가 끊기면 완료 처리를 하지 않으며 다시 시도할 수 있다.

일반 브라우저에서는 사용자가 저장 대화상자를 취소했는지, 운영체제 디스크에 파일이
실제로 저장되었는지 웹앱이 확인할 수 없다. 이 기능의 ‘다운로드 완료’는 브라우저의
전체 파일 수신과 다운로드 시작을 뜻한다. 삭제 후에는 서버에서 다시 받을 수 없다.

## 파일 제한과 저장

- 한 메시지에 파일 한 개, 파일당 최대 4 MiB(4,194,304바이트)다.
- 관리자가 설정한 첨부파일 허용 확장자와 더 작은 크기 제한이 있으면 함께 적용한다.
- 요청 전체 크기도 제한해 multipart 필드로 파일 제한을 우회할 수 없게 한다.
- 클라이언트에게 저장소 키, 서비스 키, 공개 다운로드 URL을 제공하지 않는다.
- 기존 첨부파일 저장 함수를 통해 저장한다. `ATTACHMENT_ENCRYPTION_KEY`가 설정된
  환경에서는 AES-256-GCM으로 저장 전 암호화하며, 키가 없는 환경에서는 기존 저장소
  동작을 따른다.

4 MiB 상한은 서버를 경유하는 파일 전송에 적용한 제품 제한이다. Vercel Functions의
요청·응답 본문 제한은 4.5 MB이므로 multipart 부가 데이터에 여유를 둔다.
더 큰 파일을 지원하려면 인증된 직접 업로드와 다운로드·삭제 정책을 함께 설계해야 한다.
[Vercel Functions 제한](https://vercel.com/docs/functions/limitations#request-body-size),
[Vercel 대용량 전송 안내](https://vercel.com/kb/guide/how-to-bypass-vercel-body-size-limit-serverless-functions).

## 접근과 재시도

업로드·다운로드·완료 요청은 로그인한 재직 직원만 실행할 수 있으며 같은 출처의 요청인지
확인한다. 다운로드는 대화 참여자만 가능하고 관리자 권한으로 우회하지 않는다.
파일은 브라우저에서 직접 실행하거나 미리보기하지 않고 첨부 다운로드로 응답한다.

동일 전송 요청의 재시도는 기존 메시지를 돌려준다. 같은 요청 ID에 다른 직원, 본문,
파일 메타데이터 또는 파일 내용이 들어오면 충돌로 거절한다. 파일 내용 비교는 서버가
파일 바이트에서 계산한 SHA-256으로 하며, 삭제 후에도 재시도 판별용 해시는 유지한다.

수신자 다운로드는 2분 유효기간을 가진 전송 권한으로 중복 요청을 제어한다. 완료 요청은
발급된 권한을 확인하고 반복 요청에도 같은 삭제 결과를 반환한다. 삭제 중에는 다시
다운로드할 수 없다. 저장소 삭제에 실패하면 저장 경로를 유지해 후속 요청에서 재시도하고,
실제 삭제에 성공한 뒤 저장 경로를 지운다.

저장소 오류로 삭제가 미뤄지면 ‘삭제 중’ 상태를 유지하며 이후 참여자의 채팅 목록·대화
조회에서 다시 처리한다. 별도 백그라운드 작업을 운영하지 않으므로, 모든 참여자가 앱을
닫아 둔 동안에는 후속 삭제 재시도가 실행되지 않는다. 만료된 다운로드 권한은 다른
다운로드가 새 권한으로 교체하기 전까지 기존 전체 수신 완료 확인에 사용할 수 있다.

저장소 쓰기와 DB 기록은 서로 다른 시스템이다. DB 저장 실패 시 업로드한 객체를
보상 삭제하지만 이 삭제까지 실패하면 객체가 남을 수 있다. 이 드문 이중 장애는
`Staff chat orphan file cleanup failed` 로그로 알리며 자동 복구를 보장하지 않는다.

## 검증과 적용

회귀 검증은 `tests/staff-chat-files.test.mts`에서 인증과 참여자 제한, 재전송 내용 충돌,
다운로드 권한과 중복 완료, 전송·삭제 실패 복구, multipart 크기 제한을 다룬다.
실제 서비스·라우트·multipart 파서를 실행하고 DB와 저장소는 메모리 대체 구현을 사용한다.
운영 직원·메시지·파일을 만들거나 운영 DB에 접속하지 않는다.

2026-09-08 검증: 파일 회귀 테스트 18개와 기존 채팅 API 테스트 10개, 총 28개 통과.
검증 명령은 다음과 같다.

```powershell
node --import ./tests/tsx-loader.mjs --test --experimental-test-isolation=none tests/staff-chat-files.test.mts tests/staff-chat.test.mts
```

전체 단위 테스트 715개, ESLint, TypeScript 검사, 프로덕션 빌드가 통과했다.
실제 Supabase 저장소에는 무해한 42바이트 테스트 파일만 저장·읽기·삭제했으며,
바이트 일치와 삭제 후 404를 확인했다. 기존 직원·메시지·파일은 변경하지 않았다.

2026-09-08 운영 DB에 `20260908010000_add_staff_chat_attachments`를 적용했다.
적용 체크섬 일치, 미적용 로컬 마이그레이션과 실패 마이그레이션 없음, 첨부 테이블 RLS
활성화와 공개 정책 없음, 인덱스 3개·CHECK 제약 3개·외래키 1개를 읽기 전용으로 확인했다.
앱 배포 완료 여부는 이 DB 적용 결과와 별도로 배포 상태에서 확인한다.

스키마 변경을 포함하므로 배포 대상의
`prisma/migrations-postgresql/20260908010000_add_staff_chat_attachments/migration.sql`을
먼저 적용하고 Prisma 클라이언트를 생성한 앱을 배포해야 한다. 이 문서나 단위 테스트 실행 자체는 운영 DB를
변경하거나 배포하지 않는다.

## 브라우저 검증

2026-09-08, `e2e/staff-chat.spec.ts`의 기존 채팅 시나리오 6개와 파일 시나리오 8개를
데스크톱·모바일 두 프로젝트에서 검증했다. 실제 `StaffChatDock` 컴포넌트를 격리 서버의
`/` 경로에서 실행하고 직원·메시지·파일 API를 모두 가상 데이터로 대체했다. 운영 DB,
실제 직원 메시지, 운영 파일 저장소에는 접근하지 않았다.

최종 컴포넌트 구조·CSS·삭제 안내 문구를 반영한 전체 실행에서 28개 모두 통과했다
(40.4초). 작은 높이에서는 메시지와 입력 영역을 스크롤하여 접근하도록 하고, 320px에서
세로 스크롤바로 창이 화면 밖으로 밀리는 문제를 수정한 상태다. 테스트 파일의 ESLint도
통과했다.

```powershell
npm.cmd run test:chat
npx.cmd eslint e2e/staff-chat.spec.ts
```

화면 검수는 생성된 스크린샷을 직접 열어 확인했다.

| 화면 | 확인한 정보와 동작 |
| --- | --- |
| 1366×768 데스크톱, 390×844 모바일 | 직원 이름·연결 상태, 파일명·크기·다운로드 동작, 선택한 첨부파일과 입력·전송 영역이 채팅창 안에 표시된다. 라이트·다크 모드를 확인했다. |
| 320×800 | 긴 한글 파일명을 줄바꿈하고 파일 다운로드·삭제 확인·취소·첨부 제거·전송에 접근할 수 있다. 세로 스크롤바가 있는 데스크톱 환경에서도 창이 화면 왼쪽으로 잘리지 않는다. |
| 683×384, 200% 확대에 상당하는 가용 영역 | 메시지의 다운로드 버튼과 입력 영역을 세로로 스크롤하여 각각 사용할 수 있다. 두 영역이 항상 동시에 보이는 것은 아니다. 다운로드 버튼, 입력란, 파일 첨부·제거·전송 동작의 전체 가시성을 확인하고 두 스크롤 위치를 별도로 캡처했다. |

데스크톱·모바일·320px에서 페이지와 채팅창의 가로 넘침을 검사하고 창의 실제 좌우 경계도
확인했다. 파일 선택·삭제 확인 상태의 채팅창 버튼은 모두 최소 44×44px이며, 주요 버튼은
잘린 부분 없이 보이는지 검사했다. 키보드로 채팅창 닫기와 실행 버튼으로 포커스 복귀도
기존 회귀 시나리오에서 확인했다.

검증한 파일 상태와 안전 동작은 다음과 같다.

- 파일만 전송, 업로드 중 중복 전송 차단, 실패 후 파일 보존과 같은 요청 ID로 재시도,
  직원별 첨부 초안 분리, 허용되지 않는 확장자·4 MiB 초과 파일 거절 및 본문 보존.
- 수신자의 삭제 안내·취소, 전송 중 다운로드 버튼 비활성, 파일 전체 바이트와 저장 파일명
  확인, 완료 후 다운로드 버튼 제거와 대화 목록의 ‘파일 삭제됨’ 표시.
- 네트워크 실패와 HTTP 200 부분 응답에서는 삭제 완료를 알리지 않고 같은 다운로드
  요청 ID로 재시도. 저장소 삭제 실패 시 파일은 다시 받지 않고 삭제 완료 요청만 재시도.
- 발신자의 다운로드는 삭제 요청을 보내지 않으며 수신자 다운로드 이후 실시간 갱신으로
  삭제 상태가 반영됨.
